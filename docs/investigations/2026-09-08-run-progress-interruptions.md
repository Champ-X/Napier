# 长任务误中断：进展、活跃度与收敛边界

调查对象：`thread_cc569c2775214d54a6cc` 的第二轮网页制作任务。
读取来源：本地服务的 thread detail API，调查快照共 1,788 条事件；原始执行记录
与产物未改动。
下面的时间均为北京时间（UTC+8），日期为 2026-09-07。

## 证据与结论

| Run | 时间 | 模型回合 | 结果 |
| --- | --- | --- | --- |
| `run_7bb7d50b3b5849249152` | 23:27:22–23:32:25 | 12 | `failed / partial`，无进展终止 |
| `run_81fe844790b64d308e99` | 23:33:21–23:33:47 | 7 | `failed / paused_budget`，无进展终止 |
| `run_cff11a10e60e4fb8be7a` | 23:33:54–23:37:50 | 14 | `completed` |

两次终止都由 `run.progress.rerouted → run.no_progress → run.failed`
链路主动产生。没有服务器重启、SSE 断开、30 分钟运行超时或 64 回合预算耗尽的
终止证据。`paused_budget` 在这里是可恢复失败的通用 outcome，不能据此认定实际
预算耗尽。第一次抓取确实出现网络超时和浏览器回退能力不可用，但这些工具级失败
本身不是 Run 终止原因。

### 1. 把语义改善当成了执行存活条件

第一次 Run 在 seq 538 创建 HTML，seq 725 成功修改同一文件。
seq 728 的进展向量同时记录：`productCount=2`、`changedDimensions=[workspace]`、
`indeterminateProductEffectCount=2`，但 `progressed=false`，停滞计数累计至 6。
原因是 effect observer 只把首次产物或带有 marginal evidence 的后续修改记为语义
进展；普通 `apply_patch` 的落盘摘要只能证明变化，不能证明产品质量改善。

这种区分对验收是正确的，但控制器直接使用同一个计数终止任务，使正常的增量创作
也承受“没有工作发生”的判定。随后 seq 759 成功启动预览服务，属于中性会话操作；
下一回合便在 seq 763–764 被停止，当时距离上次语义进展只有约 33 秒。

### 2. 验证是多步骤过程，原控制器只给一次操作机会

恢复 Run 的计数确实从零开始，并非错误继承了上一次的 7 个停滞回合。
但读取已有文件、搜索内容、发现工具、打开预览都只属于 supporting evidence。
seq 1034 成功打开工作区预览，seq 1037 达到 6 回合阈值；模型响应重定向后，
seq 1068 又成功截图，仍在 seq 1072–1073 被停止。整个恢复仅约 25 秒。

因此，单纯清零恢复状态、扩大总预算或修改当前会话的 prompt，都不能修复根因。

### 3. 内部回退次数被直接用作全局策略失败次数

第二轮的第一次模型调用只有一次 `web_fetch`。它的内部 HTTP 请求超时
（seq 390），浏览器回退报告能力不可用（seq 394）。它们是两条真实的操作记录，
但并不是模型已经尝试过两种独立的资料获取策略。

原策略因 `acquisitionAttemptCount=2`、零产出，在第一回合的 seq 402 即请求全局
收敛。单个目标及其回退失败不应过早剥夺其他来源和路线的机会。

### 4. 控制工具缺少显式进展声明

`create_plan / update_plan_step / update_plan_artifact / replan_plan` 被当作
`opaque` 工具。全局收敛后只有两个 opaque 调用名额；`list_files` 与 `create_plan`
消耗了名额，接下来的两个 `update_plan_step` 在 seq 505–506 失败，未进入实际执行。
这使负责整理计划和验收产物的控制面也受到资料获取收敛的限制。

## 通用修复

- **进展向量 v3 增加独立 activity 状态。** 新增的证据和不同的产物状态可以说明
  工作仍在推进；`progressed`、marginal evidence 和 delivery readiness 继续分别
  表达语义进展与验收状态。修改文件、截图都不会因此自动成为“验收通过”。
- **有证据支持的有限继续执行窗口。** 真正连续无新证据仍按原来的 6 回合阈值
  处理。有新证据时允许完成检查、实现、验证等连续步骤，但同一语义停滞窗口最多
  延展到 `3 × noProgressTurnThreshold` 回合，且不越过原来的 180 秒边界。
  重复读取、A→B→A、无休止产生新哈希都不能无限续期；总运行预算和工具循环保护
  仍然有效。重定向后，有近期工作证据的任务另有一次最多 6 回合 / 180 秒的收尾
  窗口，以便完成预览、检查、验收。其起点绑定首次重定向的回合和时间，不随操作
  或恢复滑动，也不把准备步骤误判成“必须在一次调用内完成”。原有的有限未知
  工具观察与失败修复规则仍然适用。
- **区分内部操作数量与模型策略回合。** 子操作的次数、失败域和成本证据完整保留；
  全局收敛在正常预算条件下至少观察两个实际发生资料获取的模型回合。
  单个目标/来源的失败熔断依然独立生效，真实预算压力也可以提前要求收敛。
- **控制面显式声明为 coordinate/control。** 计划更新和产物登记不再消耗 opaque
  名额。它们的真实进展仍由计划/产物账本事件判定，单纯调用成功不增加语义分数。
  目录与文件搜索也声明为 workspace observation，按稳定的结果摘要去重。
- **持久化与回放共用推导规则。** activity 从已验证的向量链推导，绑定 Run、完成
  回合、前驱和内容哈希。恢复不会重置这个窗口。解码器检查其计数与前驱的关系，
  拒绝重算哈希后的伪造状态以及 v3→v2 降级；保留 v1/v2 的历史解释。
